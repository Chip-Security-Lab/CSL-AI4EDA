# RTL 优化插件：安装与使用手册

适用版本：**0.5.3**（文档更新，操作与 0.5.2 一致）。正式入口是 **Windows 本地 VS Code**。用户提供 RTL，插件调用模型生成完整候选，再运行工具验证；CSL 侧栏输入和执行，右侧原生编辑器查看最佳候选。Vivado 用来管理工程、提供器件与约束并执行时序分析。

第一次使用推荐按下面顺序操作：

**安装 VSIX → 打开设置 → 检查/补齐环境 → 保存模型 → 打开示例 → 生成候选。**

## 使用前检查：两条流程分别需要什么

| 环境或输入 | 侧信道修复 | 时序优化 |
| --- | --- | --- |
| Windows 本地 VS Code、Python、Windows Icarus | 必需 | 必需 |
| 已初始化的 WSL 发行版与验证依赖 | 必需 | 必需（用于形式等验证） |
| Windows 时序 Python 依赖与知识库检查 | 不要求时序依赖 | 必需，设置按钮可准备依赖 |
| Vivado 和目标器件支持 | 独立模块不要求 | 必需；找到安装路径不代表工程已连接 |
| Vivado 工程连接 | 独立模块可不连接 | 优先自动连接；允许精确 PART/XDC 手动回退 |
| 完整 RTL、自己的模型接口/模型名/API Key | 必需 | 必需 |
| 确认真实敏感 input 端口 | 必需，一次一个 | 不要求 |
| 精确器件 PART 与有效 XDC | 独立侧信道任务不填写 | 必需，自动读取或手动提供 |

无需 CUDA、GPU、本地大模型权重、Git、Node.js 或 npm。插件内置的是运行源码及安装脚本，解释器、Vivado、WSL 和系统 EDA 软件仍由用户准备。首次依赖下载、模型调用需要相应网络；已有环境可复用，安装失败看终端实际报错。未给出固定最低内存、磁盘或任务耗时：取决于 RTL 规模及 Vivado 版本，当前没有跨机器性能基准。

**第一次可运行的检查顺序**：系统软件安装并重启 VS Code → 齿轮 / 工具环境 → 重新自动识别并检查 → 根据缺项点击对应依赖按钮 → 确认所需流程“依赖可用” → 模型保存并使用 → 打开示例。依赖检查不会调用模型，也不代表修复通过。

## 1. 需要下载哪些文件

普通用户只需拿到 `rtl-optimize-repair-0.5.3.vsix`，**不需要下载源码 ZIP，也不需要 Git、Node.js、npm 或编译扩展**。安装后，在“RTL：使用手册”中可离线查看本文；设置窗口也有“使用手册”和“打开示例”按钮。

### 已随 VSIX 内置

| 内容 | 用途 |
| --- | --- |
| 已编译的 VS Code 扩展 | 输入、候选、设置、取消、历史、Diff 和另存 |
| Python 后端与任务脚本 | 模型调用、验证组织、结果与运行日志 |
| TVGuider、RTL-SCA 研究源码 | 时序分析、侧信道分析与修复策略 |
| 规则、知识库、版本化 gadget | 检索与条件匹配；无需本地大模型权重 |
| Vivado Tcl 桥接与启动器代码 | 读取工程、自动打开正确工作区 |
| 依赖安装脚本与依赖清单 | 从插件设置页准备用户专用 Python 环境 |
| 示例、资源注释说明与文档 | 普通侧信道输入、八类实验输入和时序样例 |

### 需要使用本机安装的内容

| 环境 | 需要做什么 |
| --- | --- |
| Windows VS Code 1.100+ | 使用 Windows 桌面版，打开本地文件夹并信任该工作区 |
| Windows Python | 推荐 **Python 3.12 64 位**，作为两条流程共同的解释器；核心后端最低 3.10，时序依赖安装要求 3.12+ |
| Windows Icarus Verilog | 安装后保证 `iverilog` 和 `vvp` 在 Windows PATH 中，用于功能采样比较 |
| WSL + Ubuntu/Debian | 两条流程都通过它执行现有形式/验证工具；推荐已有的 Ubuntu 22.04 或 24.04 |
| Vivado + 对应器件支持 | 时序优化必须；独立 RTL 的侧信道任务不要求先打开 Vivado |
| 模型接口与自己的 API Key | 在插件设置窗口中保存；运行时需要网络，可能产生供应商费用 |

Windows Python、Vivado、WSL、系统工具和 API Key 不在 VSIX 内。插件可复用已有环境，并在你点击安装按钮后联网补齐依赖；不是完全离线或免系统工具的安装包。第三方 Python 包在专用虚拟环境中安装，不改全局 Python。插件更新也不应覆盖这些环境。

## 2. 安装插件

1. 打开 Windows VS Code。
2. 按 `Ctrl+Shift+X` 打开扩展，在扩展页右上角 `…` 选择 **从 VSIX 安装…**。
3. 选择 `rtl-optimize-repair-0.5.3.vsix`，安装后按提示重新加载窗口。
4. 用“文件 → 打开文件夹”打开你的 RTL 所在文件夹；确认信任自己创建的工程。
5. 点击左侧活动栏 **CSL**，点击 **＋** 新建任务。侧栏输入 RTL 并查看执行过程，右侧编辑器展示最佳候选。

找不到图标时，按 `Ctrl+Shift+P`，输入并执行 **RTL：新建优化任务**。设置入口是任务页/侧栏的“设置”，或命令 **RTL：打开插件设置**，打开的是 **CSL 侧栏内的设置弹窗**，不会占用右侧代码区。点击 × 或按 Esc 关闭；表单关闭后清空，已保存配置保留。

受限工作区只能查看已有结果，不能执行桥接、工具、安装脚本或模型请求。首版不支持 Remote WSL、SSH 或容器扩展宿主：可以调用 WSL 工具，但 VS Code 窗口本身应运行在 Windows 本地。

## 3. 第一次配置工具环境

进入 **设置 → 工具环境**，等待自动识别。已有环境通常只需检查结果，无需手填路径。

### 3.1 尚未安装 Python、WSL 或 Icarus

- **Python**：从 [Python 官方 Windows 下载页](https://www.python.org/downloads/windows/)安装 Python 3.12 64 位；安装时启用 Python 启动器/加入 PATH。安装结束后重新打开 VS Code。
- **WSL**：按 [微软 WSL 安装说明](https://learn.microsoft.com/windows/wsl/install)在管理员 PowerShell 执行 `wsl --install`，按提示重启。首次打开 Ubuntu，创建 Linux 用户名和密码，完成初始化。已有可用发行版则不必重装。
- **Icarus**：通过 [Icarus 官方安装说明](https://steveicarus.github.io/iverilog/usage/installation.html)选择 Windows 安装包。安装时把 `bin` 加入 PATH，重新启动 VS Code；在 Windows 终端执行 `iverilog -V` 和 `vvp -V` 应有版本输出。**只装 WSL 内的 Icarus 不满足 Windows 功能比较检查。**
- **Vivado**：使用 [AMD Vivado 下载入口](https://www.amd.com/en/products/software/adaptive-socs-and-fpgas/vivado.html)安装，并勾选目标 FPGA 对应器件支持。插件不会代装或处理工具授权。

### 3.2 在插件内准备 Python 和 Linux 依赖

1. 点击 **重新自动识别并检查**。未找到自定义安装目录时，展开 **高级设置：手动调整工具路径**，保存实际 Python、Vivado 或 WSL 发行版。
2. 要使用时序优化且缺少 TVGuider 依赖时，点击 **安装 Windows 时序依赖**。终端会创建专用环境、联网安装当前 BM25/TVIR 需要的包并实际检索内置知识库。**不安装 torch、transformers、GPU 环境或本地模型权重。**
3. 两条流程需要 WSL 验证环境。点击 **准备 WSL 侧信道依赖**。Ubuntu/Debian 缺少系统工具时脚本会安装 Yosys、Verilator、Icarus、g++ 和 venv，再安装 numpy/PyYAML；已有工具会复用。
4. 若终端提示 sudo 密码，输入你初始化 Linux 时设置的密码后回车；输入没有星号回显是正常的。不是 Windows PIN。
5. 安装结束后插件自动保存新环境路径并重新检查。查看 **侧信道修复 / 时序优化：依赖可用** 以及各项状态。

安装在 VS Code 集成终端执行，可看到实际下载进度与失败原因。需要停止时，使用终端的“终止任务/关闭终端”；失败后可修正网络或缺项再点安装。安装期间不能生成候选，不会调用模型。终端退出成功之后还会检查工具；“安装成功”或“依赖可用”均不等于修复成功。

专用目录：Windows 在 VS Code 插件用户存储下的 `environments/timing`；Linux 在 `~/.venvs/rtl-repair-sca`。重复点击复用专用环境，不覆盖你已有的其他虚拟环境。首次下载依赖需要能访问 Python 包源；离线电脑需事先准备对应环境，本版没有捆绑所有平台的二进制依赖包。

## 4. 配置模型

进入 **设置 → 模型 → 新建模型**，填写：

| 字段 | 怎么填 |
| --- | --- |
| 配置名称 | 自己起一个便于识别的名字，例如“实验模型” |
| 接口地址 | 供应商给的 OpenAI 兼容接口根地址，常见为 `https://你的服务域名/v1`；不要填写完整 `/chat/completions` 路径 |
| 模型名 | 供应商提供的准确模型标识，需与该接口匹配 |
| API Key | 你自己的密钥，粘贴到密码框 |

点击 **保存并使用**，回到任务页，在底部模型选择器确认已选中。已有配置可编辑、切换或删除；编辑时 API Key 留空保留原值。密钥保存在 VS Code SecretStorage，不写入工程、文档和发行包，不回显给表单。新用户必须填写自己的密钥，包内没有开发者账号。

运行会发送目标 RTL、相关工程源码、诊断及补充要求到所选接口。设置只保存连接信息；不要把 Key 写进 RTL、XDC 或补充要求。

## 5. 先用内置示例熟悉操作

在设置窗口点击 **打开示例**，或运行 **RTL：打开内置示例**。插件将示例复制到用户存储，并在一个新的 Windows VS Code 窗口打开。**这是可编辑的副本，不是扩展安装目录**；重复打开保留已修改的同名文件。

先阅读示例目录中的 `README.md`。第一次推荐 `single-rtl/register_toggle_two_hotspots.v`，敏感端口选择 **key**。这是故意植入泄露的教学电路，不是完整密码核。

实验 T02–T10 的文件和资源说明位于 `sidechannel-online/`；它们由插件自动检测，部分类型需要补充随机与份额资源，不建议用作第一次空白上手任务。完整 AES 示例也在 `single-rtl/`，不代表当前工具能修复任意 AES 实现。

## 6. 侧信道修复怎么用

### 6.1 提供 RTL

点击 **新建任务 → 侧信道修复**，左侧三个入口任选一个：

| 入口 | 使用方式 |
| --- | --- |
| 使用当前选中代码 | 在 VS Code 原 RTL 文件中选中要关注的代码，再进入任务页点击此入口；插件保留所在文件/模块作为上下文 |
| 粘贴代码 | 在左侧输入框粘贴完整 RTL；若只是片段，需要能在当前文件唯一定位，否则请用“当前选中”或提供完整模块 |
| 选择本地文件 | 选择 `.v` / `.sv`。如果该文件已打开且有未保存修改，使用编辑器内容快照 |

**不要只给没有接口和上下文的 always 块。** 片段表示修改重点，输出仍是完整目标文件。刚从 Vivado 新建的空 `.v` 必须先写入完整可解析的 RTL，再生成候选。不要把 Markdown 的三个反引号一起粘贴进去。

### 6.2 确认敏感输入

“敏感输入端口”要选 **真实承载密钥/秘密数据的 input 端口名**。

例如代码是 `input wire [127:0] key`，就选 `key`；是 `input [7:0] secret_i`，就选 `secret_i`。界面中的 `secret` 不是所有设计通用的填法。不能填写一个 RTL 中不存在的名称，也不要选择普通时钟或复位。

选择后勾选确认，表示你确认它承载敏感数据。当前一次任务只确认一个输入端口；代码或端口变化后需要重新确认。内部模块的敏感输入到工程顶层的映射不会自动猜测；带工程上下文的侧信道任务请从工程顶层开始。

### 6.3 开始执行

选择模型，可选填写“保持接口与周期行为”等补充要求，然后点击 **开始执行**。默认自动检查 T01–T10，不要求选择目标类型或开启实验开关。基线分析完成后会立即显示“已检查、检出、可生成、需补充信息”的数量；点击“查看十类分析”查看逐类状态与原因。满足前提的类型继续生成，其他类型会明确说明缺项或不支持条件。类型筛选收在“高级：限定类型”，只用于专项实验；每次新建任务恢复自动模式。**不知道的资源不能为了通过检查随意填。**

任务会固定输入，依次做基线分析、候选生成、功能比较、形式等价和同条件 RTL-TVLA。补充后重新分析是一个新任务：文件输入读取该文件当前编辑器内容及当前工程上下文，粘贴输入沿用先前完整 RTL；内容变化时必须重新确认敏感端口。原运行和产物不改写。依赖、驱动协议或语法不兼容会给出失败阶段。独立单模块不要求填写 PART/XDC，结果会说明验证范围；不因此获得工程时序证据。

对于内置 `t02.sv` / `T02.input.sv` 示例：不选类型，先点击开始执行运行自动分析。看到 T02 缺项后，点击“补充信息后重新分析”，在资源窗口填写 `mask_a, mask_b`（或点击“填入待确认的信号建议”）；只有你确认这些信号确实每周期提供外部新鲜随机值时才勾选声明，然后完成配置并生成。名称建议不会自动勾选新鲜性声明。该示例不需要填写份额分组或掩码域。模型必须满足接口、周期和 gadget 前提，候选仍可能功能失败或未改善。

T02 当前仅有单比特 AND gadget，T08 仅四位布尔到算术转换。T06/T09/T10 最高为 RTL 缓解证据。更多类型不是无条件自动修复；具体前提见 [类型支持矩阵](SIDECHANNEL_TYPES.md)。

## 7. 时序优化怎么用

### 7.1 推荐：从 Vivado 自动获得上下文

先完成工具与模型配置，然后进入 **设置 → Vivado 接入**：

1. 保存 Vivado 工程并关闭 Vivado。
2. 确认版本号，勾选“我已关闭 Vivado”，点击 **配置 Vivado 接入**。
3. 重新启动 Vivado 并打开工程，双击 `.v/.sv` 文件，通过外部编辑器打开 VS Code。
4. 在任务页/设置中确认连接的是正确工程。多个活动会话时选择对应工程；展开工程信息核对 **PART、顶层和有效 XDC**。
5. 切换 **时序优化**，提供 RTL、选择模型，点击 **开始执行**。

插件每次运行前向当前会话读取上下文，固定源码与约束；保留多个 XDC 的顺序和作用域，只生成目标文件的修改，再放回工程快照验证。相关关键路径不在目标文件时会说明，不擅自改其他文件。用户未保存的相关源码/约束也进入快照，不自动保存原文件。

该接入方式本机核对的是 Vivado 2024.1。其他版本需按实际设置结果核对；没读到活动会话时不要将“已找到 Vivado 安装”当作“工程已连接”。

### 7.2 没连接上：手动输入

时序页选择 **手动输入**，填写 **精确器件 PART** 并选择 `.xdc` 文件。

开发板商品名不等于 PART。例如界面需要的是 `xc7a35tcpg236-1` 这类精确器件标识，而不是“某某开发板”；示例标识不能用于你的实际工程。可在 Vivado 的 Project Settings 查看器件，或在 Tcl Console 执行：

```tcl
get_property PART [current_project]
```

XDC 应包含与你设计匹配的时钟及必要约束；空文件无法使用。无需自己上传时序报告，插件调用 Vivado 生成报告。只提供单模块及手动约束时，显示单模块验证范围，不代表原多文件工程已通过。

## 8. 看候选、导出与历史

任务结束后，右侧原生只读编辑器展示 **最佳完整候选 RTL**。改动行高亮并添加显示用的 `// CSL 修改标记` 注释；复制、另存与 Diff 使用实际候选原文，不包含这些预览标记。其余生成候选保留在运行目录，不在主界面逐一列出。结果区提供 **查看最佳候选、复制、另存、查看 Diff**；Diff 左侧为运行时输入快照，右侧为最佳候选，默认不自动打开 Diff。

原文件不会自动覆盖，另存也阻止覆盖输入源文件。未改善、形式证明超时或验证失败的完整候选仍可查看、复制和另存；先看醒目的评级和失败原因，再决定是否用于自己的工程。若系统剪贴板受会话限制，可使用另存。

| 看到的状态 | 含义 |
| --- | --- |
| 运行完成 | 本次流程结束，需继续看候选和验证评级 |
| 候选已生成 | 有完整候选代码，尚不说明功能或安全通过 |
| 未改善 | 测量未达到改善门槛 |
| 时序优化成功 | 同约束下时序改善且功能等必要检查满足；是否闭合、形式是否证明另列。形式超时不单独阻塞成功，明确反例、功能失败或工具失败仍保留失败 |
| 部分改善 / RTL 缓解证据 | 某些实测指标改善，但仍有残余或证据缺口 |
| 验证失败 / 未验证 | 有明确失败、超时或缺项，不当成通过 |
| 完整验证通过 | 必须由验收逻辑和实际证据满足门槛；代码可导出不代表获此评级 |

时序结果看 WNS/TNS、功能和形式状态；**WNS 仍为负就是尚未闭合**。RTL-TVLA 反映设计阶段切换活动，不是芯片物理功耗、毛刺安全或随机熵证明。候选说明是模型的主张，验证数字才是实际证据。

下方过程区按实际调用列出方法、来源、耗时与状态，点击条目展开摘要。旧历史没有记录时明确提示未记录，不补造已执行步骤。详细证据可通过结果区查看，执行日志在 Output 的 **RTL 优化与修复** 中。运行中可点击 **停止执行**，保留已产生的日志和取消状态。每个窗口同时运行一个任务。

模型行的 **历史** 可重新打开当时的输入和候选，无需再次调用模型。修改源文件不会改写历史输入快照。默认运行目录位于 VS Code 的插件用户存储 `runs`；设置中可指定其他可写绝对路径，历史不会随 VSIX 分发。

## 9. 常见问题

| 现象 | 处理方法 |
| --- | --- |
| 设置没有打开 | 运行“RTL：打开插件设置”；确认安装的是 0.5.3，并重新加载 VS Code 窗口 |
| Python 找不到 / 安装要求 3.12 | 安装 Python 3.12 64 位，重启 VS Code，再自动识别；必要时在高级区填实际 `python.exe` |
| 没有 Ubuntu / WSL 报发行版不存在 | 先完成 WSL 安装与首次用户初始化，再选择真实发行版；不要只填写一个尚未安装的名称 |
| pip 下载失败或超时 | 查看安装终端的包名及网络错误，修复网络/已配置包源后重试；不会因此标“依赖已就绪” |
| 找不到 iverilog / vvp | 安装 Windows Icarus 并加入 PATH，关闭并重开 VS Code；WSL 内也需相应工具 |
| Vivado 会话列表为空 | 完成接入后重启 Vivado，打开工程；确认 Windows 本地 VS Code 与正确工程会话 |
| PART/XDC 缺失 | 在 Vivado 核对当前综合源集/约束集，或切换手动输入实际 PART 和 XDC |
| 敏感端口没有列出 | 提供完整、可识别接口的模块；确认选的是 input 名。include/条件编译及不支持语法可能需要先整理入口 |
| “片段不能唯一定位” | 回到原文件选中代码，再用“当前选中”；或者粘贴完整模块 |
| 模型鉴权失败 / 模型不存在 | 在模型页核对 endpoint、模型名、Key 与账号权限；不要把 Key 发到日志里 |
| 模型没有返回候选 | 看输出区的格式/截断/请求错误；不会用原 RTL 冒充候选。代码过大时先使用受支持的较小完整模块 |
| 功能失败 / 形式 inconclusive | 查看反例、超时或不支持结构；允许导出候选，不表示可以安全替换原工程 |
| 八类实验没自动修复 | 查逐类型前提、随机资源和 gadget 缺项；目前只在特定代表性输入上实测部分改善 |

## 10. 更新、恢复与卸载

新版本同样通过“从 VSIX 安装”升级并重新加载窗口；模型和运行历史在用户存储中，依赖环境在独立目录中，不需要每次重装。升级后如工具检查有缺项，再运行对应依赖安装/检查。

更换已配置外部编辑器的 VS Code 安装位置、卸载插件或恢复 Vivado 默认编辑器之前：先关闭 Vivado，在 **设置 → Vivado 接入** 勾选关闭确认，点击 **恢复原编辑器配置**，再重启 Vivado。配置备份位于 `%LOCALAPPDATA%/RTLRepair/bridge`；恢复保留其他用户设置。

卸载 VSIX 不会自动删除历史、候选或专用环境。如需清理，先备份有用结果，再手动删除自己确认的用户存储/专用目录。不要删除整个 VS Code 用户目录。

## 11. 支持范围与验证状态

支持 Windows 本地、纯 Verilog/SystemVerilog，工程快照保留依赖、include、宏与多个有序/作用域 XDC。具体语法、刺激协议、形式证明和层级映射仍受后端能力限制。IP、Block Design、混合语言、Remote WSL 宿主、布局布线与物理功耗验收不在首版范围。

交付标记为 **本机验证**，不是另一台全新电脑完成首次安装的保证。实际执行过的检查及缺项见 [交付状态](DELIVERY_STATUS.md)，评级门槛见 [验收契约](ACCEPTANCE_CONTRACT.md)，八类代表性线上结果见 [线上实验结果](ONLINE_SCA_RESULTS.md)。

### 11.1 侧信道：目标评级与整体验收分开

候选的 `target_assessment` 只评价明确列出的本次目标类型。各目标基线根因非零、候选根因归零，并且接口、策略前提、功能、形式和同条件 RTL 测量通过，才显示“修复目标已达成（RTL 验证范围）”。公开输出或已分类的非目标残余独立列出，不因此降为“目标部分改善”。目标仍有残余才按目标改善情况评级；缺少逐类型证据、存在未分类根因或证明超时为未验证，功能/测量失败为验证失败。T06/T09/T10 最高显示“目标 RTL 缓解已达成（非物理安全证明）”。

`overall_assessment` 单独说明整体验收缺口；本次目标达成不改变旧 `repair_status`、全局候选选择门禁或验收契约中的完整验收条件，也不意味着其他类型、约束时序、门级或物理安全通过。历史记录从已有证据派生新显示，不改写原始 result.json，不重跑模型。复制、另存与 Diff 始终独立于评级。


## 12. 时序成功、闭合与形式结果分别怎么看

“时序优化成功”表示同约束下 WNS 改善、TNS 不回退、hold 等必要检查及采样功能满足当前门槛。**是否时序闭合另外展示**：WNS 仍负就尚未闭合，不能仅看绿色成功字样。形式 `inconclusive` 表示超时或未能证明，只作为独立提示，不会被改写成 `passed`；明确不等价反例、功能失败或工具失败仍不能判成功。完整验收和候选导出是不同概念。

例如已有 6.5 ns 约束的同快照任务，WNS −0.569 → +0.266 ns、TNS −5.662 → 0 ns，4096 周期采样通过；形式超时仍为未证明。该结果只对应这一输入和约束，不能用来证明另一份 6 ns 约束工程也闭合。
